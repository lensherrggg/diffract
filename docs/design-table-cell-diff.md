# 表格列对齐与单元格级差异设计

- 状态：已实现
- 适用版本：diffRact 0.1.0
- 相关代码：`src/matching/table.rs`、`src/result.rs`、`src/engine.rs`、`src/report/mod.rs`、`src/tui/mod.rs`
- 相关测试：`src/matching/table.rs` 中的 `matching::table::tests`、`src/report/mod.rs` 中的 `report::tests`

## 1. 背景

表格原先以“一行”为最小差异单位：先配对表格和行，再把整行文本做字符级 diff。只要出现以下情况，用户就会看到大量无关的删除/新增标记：

- 新增一列，后面所有列整体右移；
- 删除一列，后面所有列整体左移；
- 调整列顺序；
- 修改列名；
- 合并单元格导致某一列内容重复或出现空占位。

例如旧表为 `指标 | 本月 | 累计`，新表在中间插入 `备注` 后，按位置比较会把 `本月` 和 `累计` 全部判成变化。用户真正需要的是：**先按表头把列对上，再只标出值发生变化的单元格**。

## 2. 目标与非目标

### 目标

1. 表格列按表头对齐，支持列插入、列删除、列改名和列顺序调整。
2. 表格行仍按行记录，一条修改记录内部只列出发生变化的单元格。
3. 保持现有表格级对齐、行级对齐、主键、序号列、语义打分和阈值判定行为。
4. HTML、Markdown 和 TUI 三处渲染统一使用单元格差异。
5. 对合并单元格、无表头、重复表头、纯位置移动等边界保持可预期，不因列对齐回退产生额外噪声。

### 非目标

- 不改变表格的解析方式；合并单元格的展开仍由 `src/docx/mod.rs` 负责。
- 不把记录粒度改成“每个单元格一条记录”。记录仍以行为单位，便于与现有 TUI、筛选和统计兼容。
- 不比较字体、颜色、边框、列宽等格式。
- 不为单元格差异单独引入新的阈值体系。

## 3. 总体流程

```text
docx 解析
  └─ Document.tables[]（单元格已按 vMerge / gridSpan 展开）
       ↓
表对齐（保持原行为）
       ↓
列对齐（新增）
  ├─ 识别表头行
  ├─ 列名精确匹配
  ├─ 列名模糊匹配
  └─ 未匹配列按剩余顺序兜底
       ↓
构造对齐后的 RowView
  ├─ cells：按对齐后的列顺序重排、裁剪尾部空列
  ├─ normalized：用于行比较的归一化文本
  ├─ key：从选定的主键列取值
  └─ text：原始顺序的行文本，仅用于记录展示
       ↓
行对齐（保持原行为）
  ├─ 主键精确配对
  ├─ 整行文本精确配对
  └─ 保序相似度 DP
       ↓
状态判定 + 单元格差异生成（新增）
  ├─ 对齐后文本相同：未变 / 移动
  ├─ 无变化单元格：移动 / 跳过
  └─ 有变化单元格：修改 / 疑似修改，写入 row_diff
       ↓
engine 为 row_diff 中双侧都有值的单元格生成字符级 diff
       ↓
TUI / HTML / Markdown 渲染
```

## 4. 数据结构

### 4.1 列映射

```rust
struct ColumnPair {
    old: Option<usize>, // 旧表列下标；新增列没有
    new: Option<usize>, // 新表列下标；删除列没有
    label: String,      // 展示用列名，优先新表表头
}

struct ColumnAlignment {
    pairs: Vec<ColumnPair>, // 新表列在前，删除的旧列追加在后
    old_ignored: Vec<bool>, // 旧表序号列
    new_ignored: Vec<bool>, // 新表序号列
}
```

`ColumnPair` 的一侧为 `None` 时表示整列新增或删除；`row_cell_changes` 会把它转换成 `CellChange.old` 或 `CellChange.new` 为空。

### 4.2 行视图

`RowView` 同时保留两套文本：

- `cells`：按 `ColumnAlignment.pairs` 重排后的单元格，用于行相似度、主键和单元格差异；
- `text`：原始顺序的展示文本，用于记录列表和“整行新增/删除”；
- `normalized`：`cells` 归一化后用 ` | ` 连接，列顺序变化不会造成误判；
- `key`：从两表都选中的主键列取值。

这样既不破坏原有展示，又让比较发生在统一列序上。

### 4.3 单元格变化

```rust
pub struct CellChange {
    pub column: String,       // 对齐后的列名
    pub old: Option<String>,  // 空字符串转为 None
    pub new: Option<String>,
    pub diff: Option<ParaDiff>, // engine 后处理阶段填充
}
```

`Record` 新增：

```rust
pub row_diff: Option<Vec<CellChange>>,
```

非表格记录保持 `None`；表格修改/疑似记录写入非空 `row_diff`。`Record.diff` 仍保留整行字符级差异，用于没有单元格差异时的兼容路径，但报告和 TUI 优先使用 `row_diff`。

## 5. 算法

### 5.1 表头识别

实现：`header_row`。

1. 按列数生成序号列标记 `old_ignored` / `new_ignored`。
2. 在前三行中找第一行“非序号列的非空单元格数 ≥ 2”的行作为表头。
3. 如果找不到，回退到第 0 行；空表返回 `None`。

这样可以处理常见的中文表格结构：

```text
┌──────────────────────────────┐
│        2026 年指标完成情况        │  ← 跨列合并的标题行，跳过
├──────┬──────┬──────┬─────────┤
│ 类别 │ 指标 │ 本月 │ 累计     │  ← 真实表头
├──────┼──────┼──────┼─────────┤
│ 营销 │ 售电量│ 100  │ 200     │
└──────┴──────┴──────┴─────────┘
```

表头行本身仍作为普通行参与行对齐，因此标题行或表头行的改动也能被记录。

### 5.2 列对齐

实现：`align_columns`、`map_headers`、`map_positionally`。

表头值由 `header_values` 生成，包含所有非序号列；空列名保留为空字符串，用于后面的位置兜底。

匹配顺序：

1. **精确匹配**：列名归一化后完全相同，且两边都唯一时直接配对。
2. **模糊匹配**：对剩余列计算字符集合 Jaccard 相似度，阈值 `0.5`，按分数从高到低贪心配对。用于识别 `本月` → `本月完成`、`指标（万元）` → `指标` 这类改名。
3. **顺序兜底**：仍未匹配的旧列和新列按各自出现顺序一一配对。

如果任一侧没有任何非空表头，直接按位置对齐，避免把数据行误当表头。

配对结果按“新表列顺序”输出；新表中没有对应旧列的列成为新增列。随后把旧表中未匹配的列追加到末尾，成为删除列。这样 `build_view` 在新旧两侧都能生成等长的列序列，新增/删除列表现为一侧空单元格。

### 5.3 行主键

实现：`choose_key_columns`。

从列对齐结果中取第一个“在旧表和新表中都足够唯一”的非序号列作为行主键。判断规则沿用 `column_is_usable`：

- 非空值至少 2 个；
- 唯一值至少 2 个；
- 唯一值占非空值至少 70%。

如果主键列本身被改名，只要它仍能和另一列对齐，就仍可作为主键；无法确定时退回整行文本相似度。

### 5.4 行对齐与状态判定

实现：`align_rows`、`compare_table_pair`。

行对齐逻辑未改变，仍为：

1. 主键相同的行精确配对，允许跨顺序，以便识别移动；
2. 剩余行按对齐后的整行文本精确配对；
3. 其余行做保序 DP，分数低于疑似阈值且没有“多数单元格相同”时不允许配对。

配对后：

- `old_row.normalized == new_row.normalized`：内容未变；如果顺序变化则记为“移动”，否则跳过。
- 计算 `row_cell_changes`：
  - 为空：说明只有序号列或列顺序变化等非内容变化；顺序变化记“移动”，否则跳过。
  - 非空：按以下条件判“修改”：
    - 主键相同；或
    - 综合分达到 `threshold_modified`；或
    - 多数单元格相同（`mostly_equal_cells`）。
  - 否则判“疑似修改”。

“多数单元格相同”是单元格级差异带来的额外信号：即使整行文本相似度因主键改写而偏低，只要多数对齐后的单元格没变，仍可确认是同一行的局部修改。

### 5.5 单元格差异生成

实现：`row_cell_changes`。

对 `ColumnAlignment.pairs` 逐列比较：

1. 取旧表对应列、新表对应列的值并 `trim`；
2. 两侧相等，或两侧都为空，跳过；
3. 否则生成 `CellChange`：
   - `column` 使用 `ColumnPair.label`；
   - 空字符串转为 `None`；
   - `diff` 暂不生成。

`ColumnPair.label` 的取值顺序：

1. 新表表头文本；
2. 旧表表头文本；
3. `第N列`。

因此新增列显示新列名，删除列显示旧列名，改名显示新列名。

### 5.6 字符级 diff 的生成时机

`engine.rs` 在记录排序和编号之后统一处理：

- 修改/疑似记录仍生成整行 `record.diff`；
- 如果存在 `row_diff`，对每个新旧值都非 `None` 的单元格生成 `ParaDiff`。

只有一侧有值的单元格（新增列/删除列）不做字符级 diff，渲染时直接展示单侧值或 `—`。

## 6. 渲染

### 6.1 TUI

实现：`cell_comparison_lines`、`cell_side_lines`。

- 修改/疑似表格记录优先走单元格差异视图；
- 顶部提示“仅显示有变化的单元格”；
- 每个变化格按 `列名：值` 展示，旧侧红色/删除线，新侧绿色；
- 单元格 diff 仍受 `expanded` 和 `context_chars` 控制；
- 新增列在旧侧显示“（无）”，删除列在新侧显示“（无）”。

### 6.2 HTML

实现：`render_cell_changes_html`。

- 输出三列表格：列、旧值、新值；
- 列名、文本都经过 `escape_html`；
- 有字符级 diff 时用 `<del>` / `<ins>`；
- 单侧缺失显示 `—`；
- 修改/疑似记录不再输出整行文本 diff。

### 6.3 Markdown

实现：`render_cell_changes_markdown`、`cell_side_markdown`、`markdown_cell`。

- 输出标准 Markdown 表格：`| 列 | 旧值 | 新值 |`；
- 单元格内的 `|` 转义为 `\|`；
- 新增/删除用 `<del>` / `<u>` 标记；
- 换行转为 `<br>`，保证表格不被打断。

## 7. 边界与失败模式

| 场景 | 行为 |
| --- | --- |
| 插入空列 | 通常只产生表头一条修改记录 |
| 插入有值列 | 表头 + 该列实际有值的每一行各一条记录 |
| 删除列 | 表头 + 该列有值的行记录删除的单元格 |
| 仅改列名 | 通常只有表头一行记录 |
| 仅挪列 | 不产生记录（行内容按列序对齐后相同） |
| 挪列同时改值 | 只记录变化单元格，列名按新表头 |
| 合并标题行 | 自动跳过标题行，使用下一行作为表头 |
| 纵向合并单元格 | 解析阶段已展开到覆盖的每一行；单元格差异按行报告 |
| 横向合并单元格 | 占位列内容为空；不产生内容差异 |
| 序号列重编号 | 序号列不参与列对齐和单元格比较，不产生差异 |
| 无表头/表头全空 | 退回按位置对齐 |
| 表头重名 | 精确匹配跳过不唯一列名，剩余列按顺序兜底 |
| 删一列同时加一列 | 极端情况下会被识别为列改名；README 已注明 |
| 表头整体重写 | 可能退化为按位置对齐；不保证语义上的列身份 |

已知限制：

- 合并单元格内容变化会按覆盖的每一行分别报告，暂不合并成一条。
- 表格级对齐仍使用原始行签名和首列键；列对齐只影响行内比较，不改变表对齐算法。
- 行内多处修改仍合并为一条记录。

## 8. 性能

- `align_columns` 对每对已匹配的表格执行一次，列数通常很小；表头匹配为 O(列数²)，不影响整体复杂度。
- 行对齐、DP 和相似度计算仍是主要开销，未新增逐单元格的独立匹配阶段。
- `row_cell_changes` 只遍历列，复杂度 O(行数 × 列数)，与原来的整行文本比较同量级。
- 单元格字符级 diff 只在修改/疑似记录上生成，且只对双侧都有值的单元格生成，不会扫描未变化表格。

## 10. 备选方案

### 方案 A：仍按整行文本 diff，只在展示层高亮

实现成本最低，但无法解决插入列导致的整行错位，用户仍会看到大量伪差异，不满足需求。

### 方案 B：按列位置对齐

无法处理插列、删列和挪列；只要中间插入一列，后续列全部错位，与现状差别不大。

### 方案 C：只按精确表头名对齐

改列名会被当成“删除旧列 + 新增新列”，整列数据都会被重复报告，噪声仍然很大。因此增加模糊匹配和顺序兜底。

### 方案 D：每个变化单元格一条记录

定位最精确，但会改变记录粒度、统计口径、TUI 筛选和 `matched_to` 语义，且同一行的多处修改会被拆散。最终选择保留行级记录，在记录内部携带 `row_diff`。

## 11. 后续可扩展

- 合并单元格变化按合并区域聚合为一条记录。
- 多级表头（两行表头）按列路径拼接列名。
- 把列对齐结果暴露到日志或调试输出，便于排查表头重名场景。
- 为“删一列 + 加一列”与“列改名”增加更明确的置信度判断。
